    How to read this

    This browser requests /api/ping on every target at a fixed interval. Nothing is stored on the server: all timers and counters live in this page, so keep it open and visible, and do not reload during a test. The log and the counters are also saved in this browser every few seconds, so an accidental reload loses the timeline but not the numbers.

    The timeline keeps the last 6 hours. Choose a preset span or type your own, from 30 seconds to 6 hours; step back and forth with the arrows, or drag across the chart to zoom in on a stretch. "Export all (JSON)" saves the whole run, including the per-second data behind the timeline, and "Open a saved run" shows such a file again later.

    Tile states

    ok
    Answered in time, by all the pods that are expected.
    slow
    Answered, but slower than the slow threshold.
    degraded
    Every request is answered, but by fewer pods than expected. The service is up on reduced redundancy: this is what the replicas buy you while a node is away.
    failing
    Requests fail, but not yet enough in a row to be an outage. If they stop failing first, the log records them as failed requests: a glitch, not an outage. Failures that keep coming back are one log line, from the first failed request until ten seconds have passed without another; while it runs, the line shows the count so far.
    outage
    Enough requests in a row have failed. An outage runs from the first failed request to the first one that is answered again, so its length is known to within one probe interval. A request that times out is only known to have failed once the timeout has passed, so an outage of timeouts appears that much later, with its true start time.

    Inside the cluster

    The verdict for the inside is taken over all pods together. It is an outage only when no reporting pod gets an answer from the Service; failing when the Service answers but some of the requests to it fail, as in the time after a node dies while the Service still sends requests to the pod that was on it; degraded when something is missing but requests are answered (a pod or node that is away, a pod the others cannot reach, fewer pods answering than expected); and unknown when no report arrives, which is what happens when the outside is down. One or two failed requests are a glitch: logged, but not a change of verdict. The node list says, for each node, whether its pod reports and whether the other pods reach it; when one node is down, that is where the others agree on which one.

    The table shows what each pod measures from the inside, collected through whichever external target is up. Each request from this page reaches one pod, so a pod's report is normally one to three seconds old; the age is under the pod's name, in amber once it passes 8 seconds. A column whose pod has not reported for 15 seconds is marked as having no report; that is expected while its node is down. A cell says so, with the same limit, when its own latest result is more than 8 seconds old, and its tooltip always gives that age. The pods count from their own start, so their numbers begin again after a restart, and they tell more failure classes apart than a browser can: conn_refused, dns_error, tls_error and other_error in place of network_error.

    Service, kept-alive
    One connection that is reused. It stays on the pod it first reached, so it shows what an established client experiences.
    Service, new connection
    A new connection for every request, balanced over the ready pods. Degraded when fewer pods answer than expected.
    Pod
    Each pod asked directly by its IP, past the Service, and whether it is a ready endpoint of the Service at that moment.
    Down, but still sent requests
    The other pods cannot reach it, yet the Service still lists it as ready: requests keep being sent to a dead pod until the cluster notices.
    Alive, but out of the Service
    It answers, but is not a ready endpoint: starting up, or shutting down gracefully.
    API server
    The API server's health endpoint through its internal Service, with a new connection each time. That Service spreads requests over the API server on every control-plane node, and a request cannot tell which node it was sent to. So when one control-plane node is down, every pod sees some of its requests fail until the cluster stops sending them there: those failures belong to the node that is down, not to the pod that counted them. It does not affect the verdict for the inside.

    What a failed request means for a client

    The pods tell two kinds of timeout apart, because they call for different reactions. Each pod also retries a failed request once, on a new connection, to show what a client that retries would get; the first attempt is still what is counted as failed.

    timeout_connect
    The connection did not open in time, so the request was never sent. This is what a node that is powered off looks like: it answers nothing at all. Nothing reached the server, so sending the request again cannot do anything twice.
    timeout_response
    The request was sent and no answer came in time. The client cannot know whether the server acted on it, so only a request that is safe to repeat should be sent again.
    conn_refused
    The node is up but nothing listens: the pod is gone. Fails at once, and nothing was sent.
    http_503 and others
    A response arrived with that exact status. From outside, the browser can only see the status of a failed answer on the address this page was loaded from; a failed answer from the other address lacks the permission headers and shows as network_error.

    Why a request failed

    http_5xx
    A 5xx status, usually from the router or gateway when it has no healthy backend.
    http_other
    Any other unexpected answer.
    timeout
    No answer within the timeout.
    network_error
    The request failed before any HTTP answer arrived. A browser cannot tell DNS failures, TLS failures, refused or reset connections and CORS rejections apart, so they all appear as this one class. If a target shows only network_error from the start, open its URL in a new tab once: an untrusted certificate fails this way.

    Numbers on a tile

    Availability
    The share of requests that were answered at the first attempt.
    Fine on a retry
    Of the failed requests, how many were answered when this page sent them once more straight away, as a web application that retries would. The retry goes over the connection the browser already has to the route or gateway; a page cannot make the browser open a new one. It is the route or gateway that then picks a pod again.
    Latency p50 / p99
    Half of the answers, and 99 % of them, were at least this fast. Accurate to about 5 %.
    Measurement gap
    Time when this page could not measure properly: the tab was in the background, the computer slept, or the page was reloaded. Outages that overlap a gap say so in the log.
